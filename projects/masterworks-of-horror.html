Overview

Masterworks of Horror is a real-time PvP card battler set in the public-domain horror canon of Lovecraft, Poe, and others. It runs server-authoritative on dedicated servers, so a competitive match is decided by the server, never the client.

I joined as technical producer and engineer. I own the online layer and the build and release pipeline, and I built the studio's tooling for running a team of human engineers alongside AI coding agents.

Part I · Chapter 01

Competitive integrity, in real time

The board · a real-time literary duel

The tension that shapes everything

A competitive card game has to be cheat-proof, which points straight at dedicated servers and a server that owns the truth. The client is never trusted. But this game is real-time, not turn-based, so it also has to feel instant under a player's hands.

Those two goals pull against each other. Everything below is how that tension got resolved: authority on the server, responsiveness on the client, and a deploy pipeline that keeps a live fleet honest.

Chapter 02

Server-authoritative netcode

A turn resolving · server-driven, client-rendered

The server owns the truth

Built on Unity Netcode for GameObjects with a dedicated-server build, talking plain UDP over UnityTransport. There is no peer-to-peer and no relay.

Every player intent is a server RPC: ready a deck, mulligan, play, concede, rematch. The server is the only thing that mutates game state, then broadcasts the result. It validates and rejects, so a client trying to pause a ranked match simply gets refused. I am the top author of the player command surface and the replicated match model, and I wrapped the whole dedicated-server lifecycle behind one interface so the backend could move from Unity hosting to PlayFab without touching gameplay.

Chapter 03

Making it feel instant

Optimistic play · the card moves before the server answers

Prediction, then reconcile

A server-authoritative game can feel laggy if the player waits for a round trip on every action. So I built a client-side prediction system: drag a card and it plays locally right away, with the cost subtracted from your hand instantly. When the server confirms, the prediction swaps in the authoritative card and skips the redundant animation. When the server rejects, the card rolls back to your hand. It only ever touches visuals, never the authoritative model.

The piece that makes prediction free: I removed the old habit of pausing the server to wait for client animations. The simulation now ticks continuously at 50 Hz and animations are purely cosmetic, so they can never block or desync the real game state.

Chapter 04

The dedicated-server fleet

Live matches, allocated on demand

Hosting, matchmaking, and a one-button deploy

I own the entire online-services layer. A server build registers with the PlayFab game-server SDK, signals that it is standing by, waits for an allocation, and resolves its own UDP port so several servers can share a machine. Matchmaking runs through PlayFab queues for ranked, private, and solo-versus-bot, with the wait time estimated from a rolling average. Sign-in is anonymous, so there is no signup wall in front of a match.

Releasing all of that is a single 910-line Python tool I wrote. It packages the Linux server, uploads it, creates the build, and flips the live matchmaking queues over, with subcommands to scale capacity, SSH into a hot VM, and pull post-mortem logs from a terminated session. The fleet also defends itself: reconnects outlast the engine's async shutdown, the matchmaker retries transient failures with backoff, and idle servers shut themselves down after thirty seconds.

Part II · Chapter 05

War stories from shipping

The impressive part of a game is not the gameplay. It is that it ships to three stores at all. A sample of the fixes that got it there, in the commit messages they were written with.

The Android heap cap

Unity 6 hardcodes a 4 GB heap on the Gradle launcher. Our 7 GB app bundle ran it out of memory at the signing step. I made Gradle emit an unsigned bundle and signed it afterward under a 12 GB heap, keeping the keystore password in editor session state so it never touches disk.

69fabd1e6 · launcherTemplate.gradle

One wrong character

Cold-start deeplinks on iOS silently never fired. The injected scene-delegate method used willConnectTo: instead of the real willConnectToSession:. iOS never called it, so every deeplink that launched the app from cold was dropped.

0cdc5380f · iOS UISceneDelegate

A NaN that never left

A divide by a zero-sized screen rect produced a NaN before layout settled. Because the gyro offset is smoothed with a lerp, and a lerp of a NaN stays a NaN, one bad frame poisoned the parallax on every card forever. Fixed at the source, with a self-heal so a poisoned session recovers.

dd7f9467d · CardParallaxService

640 MB back

The tutorial ran iOS out of memory. I traced it to the texture cache and made it platform-aware: load on demand, clear the cache on entering a match (which needs about fourteen textures), and cap it. Recovered roughly 640 MB.

652f293ff · Card3D texture cache

The ProjectSettings trap

A teammate bumped the Android version code, built, and the store rejected the bundle: version already used. The post-build git restore was quietly reverting ProjectSettings/, including the version bump. I traced it, proved the entry was redundant, and removed it.

4c39060cd · BuildProcessor

The build pipeline itself

Five targets from one Build Console: iOS, Android, Windows, Mac, and a Linux dedicated server. Dev and Prod swap config at build time, and a precompressed texture-sidecar pass strips about 1.5 GB of card art from every device build.

A bot with opinions about 40 cards

The opponent bot is not a generic search. It is a hand-tuned scoring engine, about 4,300 lines, that routes ordinary cards through generic value functions and gives roughly forty named cards their own branch. Four difficulty tiers map to how fast it acts, from a ten-second beat down to two.

It also produced my favorite debugging story. A single typo, value -= -5000, made the bot value drawing at +5000 when its hand was full, so it would draw over its own cap and then refuse to play anything. The infamous frozen bot, fixed by one sign and a live hand count.

A hidden observation tool

I also built an in-game spectator and free-cam suite, invisible in shipped builds, flipped on by a build flag and a backquote key so it never shows in a screenshot. One feature mirrors your own board to render exactly what your opponent sees, which is how we debugged a real-time duel from both sides at once.

Part III · Chapter 07

Producing humans and agents

I treated every AI failure mode as a producer problem, not a model problem.

As AI coding agents arrived, the new friction was not the code they wrote. It was the seams: where an agent hands off to a human and the handoff breaks. As technical producer I built the tooling that closes those seams. It runs entirely on a Mac mini behind a tunnel, with a local database and zero cloud cost.

The pipeline I built and proved on the real game

Idea — raw text, no AI

Capture is free. Nothing runs until you choose it.

Diagnose — opt-in Opus pass

One click enriches the task. Then queue it to FROST.

FROST — isolated worktree branch

Opus implements, committing after each step.

Review — a second Opus pass

Merge, fix, or redo. One auto-fix, then re-review.

Stuck? — one focused question

Instead of failing silently, FROST asks a single under-180-character question and the task re-enters the queue with your answer.

Pull request — opened with review inline

A human's first contact is a clean, already-reviewed PR.

Mechanism

Necronomicon · the human team's board

Two surfaces, one site

FROST lives inside Reveries, a low-friction surface for capturing an idea and shipping it through the agent. Alongside it I built Necronomicon, the human team's production tool: sprints, a kanban board, epics, and metrics computed in SQL, with velocity and a daily burndown.

A solo idea captured in Reveries can be promoted straight onto the team's sprint board. One path, from a lone thought to a shipped pull request to the team's plan.
